  Spectral Dynamics Wildcat2 Image
  EVAL-AD4080-FMC on the Digilent Genesys ZU-5EV (Zynq UltraScale+ XCZU5EV)
  ===================================================================
  Derived from the ADI ad4080_fmc_evb ZedBoard reference project, retargeted
  to the Genesys ZU-5EV carrier. Reuses the Wildcat (AD7383-4) backhaul:
  10G SFP+ (open MAC + TCP checksum offload), USB IIO gadget, WiFi AP,
  USB-stick auto-updater, RGB status LED, and the fast headless boot.

  HDL repository: https://github.com/analogdevicesinc/hdl
  HDL branch: main

  Linux repository: https://github.com/scottcolson1968/Wildcat
  Linux branch: main

  ADC: AD4080 -- 20-bit, 40 MSPS differential SAR, LVDS (DCO + DA/DB) interface.

  1.2    (2026-08-04)  Wildcat2 target operating point: 4.096 MSPS.

         Clock chain retuned from the ADI reference point (400 MHz / 40 MSPS,
         used during bring-up to remove our clock tree as a variable) to the
         Wildcat2 target. Only the ADF4350 frequency changes -- the AD9508
         dividers were already correct, so the 10-clocks-per-sample ratio is
         preserved:
             ADF4350        327.68 MHz EXACTLY
                            channel-spacing 40 kHz -> MOD = 25 MHz / 40 kHz
                            = 625, zero frequency error (100 kHz spacing
                            cannot express 327.68 MHz; the power-of-two FFT
                            frame needs it exact)
             OUT3 /1        327.68 MHz  -> LVDS interface clock (DCO)
             OUT2 /10        32.768 MHz -> CNV = 32.768 MSPS conversion rate
             OUT0 /10        32.768 MHz -> FPGACLK
             sinc5+pf1, OSR 4 = decimation 8  ->  4.096 MSPS

         CLK and CNV must be scaled TOGETHER. Halving OUT3 alone (200 MHz DCO
         with CNV left at 40 MHz) was tested and killed the lanes outright:
         the part needed 800 Mbps of launch bandwidth while the clock could
         only carry 400.

         Validated at the target rate:
         - alignment window 191..511 (321 taps wide), tap 351
         - sampling_frequency reads 4096000
         - local capture 4.05 MSPS at both -b 1024 and -b 16384
         - 10G, -b 16384, 80M samples: 19.58 s vs 19.53 s ideal =
           4.0866 MSPS = 99.77%, 16.35 MB/s, no overflow, iiod ~44% of one core
         - 1G, -b 16384: 3.95 MSPS (96.4%) -- borderline, would slowly fall
           behind; 10G remains the transport
         - buffer size still dominates the NETWORK path: at -b 1024 each
           buffer costs a ~0.9 ms libiio-0.26 round trip (single buffer in
           flight), capping it at ~1.1 MSPS on 10G and 1.64 MSPS on 1G
           regardless of link speed or sample rate. Locally the constraint is
           free at this rate -- 1024 and 16384 both give 4.05 MSPS.

         Note the ~26 MB/s ceiling measured on the iiod path at large buffers
         is well under what this 10G link has delivered before (~200 MiB/s),
         so there is headroom to recover if higher aggregate rates are needed
         -- relevant for the 16-channel plan, where 16 x 4.096 MSPS x 4 B is
         ~262 MB/s.

  1.1.0  (2026-08-04)  FIRST WORKING AD4080 CAPTURE on the Genesys ZU-5EV.

         Root cause of the long-standing "Data alignment process failed"
         (-110): the UltraScale+ branch of library/xilinx/common/ad_serdes_in.v
         hardcodes .DATA_WIDTH (8) on ISERDESE3, ignoring SERDES_FACTOR. The
         7-series ISERDESE2 branch passes it correctly. ad408x_phy asks for
         SERDES_FACTOR(4) and drives CLKDIV = clk/2, which delivers only 4 new
         bits per CLKDIV; an ISERDESE3 built for 8 bits per CLKDIV but clocked
         twice as often repeats every bit across two output words. The packer
         therefore assembled its 20-bit word from 10 real ADC bits, so no
         shift_cnt (0..19) and no IDELAY tap (0..511) could ever match the
         0xAC5D6 training pattern. Measured on the wire as a 40-bit period
         where 20 was expected (perfect 20-bit period after decimate-by-2).

         The fix is one line, in a LOCAL copy of ad_serdes_in.v under
         library/axi_ad408x/ (the shared file is left untouched -- four other
         IPs use it). The Q mapping must NOT be changed: in 4-bit mode the
         valid bits are Q[7:4], exactly where data_s0..s3 already sit.
             -  .DATA_WIDTH (8),
             +  .DATA_WIDTH (SERDES_FACTOR),

         This also affects ADI's own admx6001_ebz/vcu118 (AD4080 via
         axi_ad408x at SERDES_FACTOR(4) on Virtex UltraScale+) -- worth
         reporting upstream.

         Results:
         - IDELAY alignment window 203..511 (309 taps wide), tap 357
         - ad4080 probes; iio:device4 present; real converted data
         - local capture 156.0 MB/s = 39.0 MSPS (97.5% of the 40 MSPS max)
         - 5 MSPS (sinc5+pf1, OSR 4 = decimate by 8) over 10G with a 16k
           buffer: 19.7 MB/s = 4.91 MSPS sustained over 20 s, 98.3%, no
           overflow, iiod at 44% of one core
         - buffer size dominates the network path: at 1024 samples each
           buffer costs a ~0.9 ms libiio-0.26 round trip, capping it at
           ~1.1 MSPS on 10G and 1.66 MSPS on 1G regardless of link speed

         Other fixes in this release:
         - axi_ad408x.v: DELAY_CTRL_DRP_WIDTH is 9 on UltraScale/UltraScale+
           and 5 on 7-series (was hardcoded 5), matching axi_adrv9001's own
           ternary, and the width is now propagated into ad408x_phy -- an
           18-bit DRP bus was being driven into a 10-bit port.
         - library/axi_ad408x/Makefile: XILINX_DEPS tracks the ad_serdes_in.v
           that axi_ad408x_ip.tcl actually compiles. When those two disagree
           make silently no-ops (exit 0, no output, and the ADI makefile
           deletes *.log), so a stale bitstream gets tested. Always confirm
           system_top.bit was regenerated before deploying.
         - ad408x_phy.v / axi_ad408x.v: ILA debug taps (serdes_data_8,
           ad_pack_odata_20, adc_data_shifted, and a state word carrying
           serdes_reset_s / shift_cnt / device_code). Observation only.
           Strip these for a production build.
         - device tree: adi,num-lanes = <1> with AD9508 OUT3 /1 (400 MHz DCO),
           matching the ZedBoard reference. 200 MHz DCO was tested and kills
           the lanes entirely -- the part requires the 400 MHz clock.

         Diagnostic note: adc_data at the IP boundary is GATED by the channel
         enable. Any ILA capture of it reads 0x00000000 unless
         0x80010400 is set to 0x51 (ENABLE|FMT_EN|FMT_SIGNEXT) first. This
         invalidated an entire day of measurements before it was spotted.
